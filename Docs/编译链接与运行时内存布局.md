# 编译链接与运行时内存布局

## 整体流程与构建产物

嵌入式程序中各个函数和变量的地址分配并不是由编译器单独决定的，而是连接器根据连接信息进行地址安排，大致工作过程如下：

```text
芯片硬件手册
    定义 Flash、RAM、外设等物理地址
            ↓
编译器与汇编器
    将各源文件转换为目标文件，并按用途生成输入段
            ↓
链接器和链接脚本
    合并输入段、完成符号重定位，为输出段分配运行地址和加载地址，
    生成 ELF 和 Map，并可进一步转换为 BIN、HEX
            ↓
处理器复位与启动代码
    处理器从向量表取得初始主栈指针和复位入口；
    启动代码完成必要的芯片初始化，复制 .data、清零 .bss，
    建立 C/C++ 代码所需的基本运行环境
            ↓
RT-Thread 内核初始化
    初始化内核对象、时钟节拍、调度器和系统线程；
    根据配置建立系统堆、内存池或其他内存管理机制
            ↓
应用初始化与调度运行
    创建或启动应用线程，启动首次调度；
    线程栈、异常栈以及静态或动态内存在运行过程中被实际使用
```

因此，物理地址范围由芯片硬件决定，代码和静态对象的最终地址由链接器确定；复位后，启动代码依据链接结果建立初始运行环境，而线程栈深度、堆块分配等动态状态只有在系统运行时才能确定。

在完成编译和链接后，工程通常会生成 `.elf`、`.bin`、`.hex` 和 `.map` 文件。它们描述的是同一份程序，但服务于不同环节：

| 文件 | 主要作用 | 是否包含目标地址 | 典型用途 |
|---|---|---:|---|
| `.elf` | 保存程序段、加载地址、符号表以及调试信息，是信息最完整的构建产物 | 是 | GDB 调试、反汇编、分析段和符号、生成其他固件格式 |
| `.bin` | 只保存连续的**原始二进制数据**，不包含地址、段名和符号信息 | 否 | 烧录工具已明确**起始地址**时下载，或用于固件传输和升级 |
| `.hex` | 以**文本记录**数据及其目标地址，通常还带有记录校验信息，可表达**不连续的地址区域** | 是 | 烧录器、生产工具或需要明确地址的固件分发 |
| `.map` | 记录链接器如何布置输出段和符号，以及各目标文件对空间的贡献 | 是 | 分析 Flash/RAM 占用、查询变量或函数地址、定位链接问题 |

这四个文件的关系：

```text
源文件
  ↓ 编译
目标文件
  ↓ 链接
ELF + Map
  ↓ 格式转换
BIN / HEX
```

其中，ELF 是**调试和程序结构分析的主要依据**，Map 是便于**人工阅读的链接布局报告**，BIN 和 HEX 则主要面向**固件下载与分发**。四者不能仅通过文件大小直接比较程序占用：ELF 可能包含不写入芯片的符号和调试信息，Map 是文本报告，而 BIN 和 HEX 的编码方式也不同。实际 Flash 和 RAM 占用应结合 ELF 的可加载段、Map 文件以及尺寸分析工具判断。

知识补充：

> **输入段**：编译器或汇编器在每个可重定位目标文件（`.o`）中生成的段，用来按用途组织代码和数据，例如 `.text.main`、`.rodata`、`.data` 和 `.bss`。链接前，同名输入段可以分散存在于多个目标文件中，其最终运行地址通常还没有确定。
>
> **输出段**：链接器按照链接脚本的规则，从各目标文件中选择并合并输入段后形成的段，例如把所有 `.text`、`.text.*` 输入段汇集为最终的 `.text` 输出段。链接器会为输出段确定内存区域、地址、对齐方式和访问属性，并将其写入最终的 ELF；因此，输入段描述的是链接器接收的内容，输出段描述的是链接器组织后的最终布局。

## 从源代码到目标文件

编译器逐个处理 `.c`、`.s` 或 `.S` 文件，生成可重定位目标文件。此时**编译器通常只知道一个函数或变量属于哪类输入段，并不知道它在整个固件中的最终绝对地址**。

常见源码对象与输入段的关系如下：

| 源码内容 | 常见输入段 | 典型属性 |
|---|---|---|
| 函数实现 | `.text`、`.text.<name>` | 只读、可执行 |
| `const` 全局对象、字符串字面量 | `.rodata`、`.rodata.<name>` | 只读 |
| 有非零初值的全局或静态变量 | `.data`、`.data.<name>` | 运行时可读写 |
| 未初始化或零初始化的全局或静态变量 | `.bss`、`.bss.<name>` | 运行时可读写、启动时清零 |
| RT-Thread 自动初始化项 | `.rti_fn.*` | 只读注册表 |
| FinSH/MSH 命令描述项 | `FSymTab` | 只读注册表 |
| 显式指定到 STM32F407 的 CCMRAM 对象 | `.ccmram`、`.ccmram.*` | CPU 专用数据，需由程序自行初始化，不能用于 DMA |

**STM32F407 的 CCMRAM** 

> CCMRAM 是一块 64 KiB 的内核耦合数据 RAM：
>
> ```text
> 地址：0x10000000
> 大小：64 KiB
> 访问者：CPU
> 特点：CPU 访问快，但 DMA 无法访问
> ```
>
> 在实际使用中，可以通过 GCC 的 `section` 属性显式指定对象所属的输入段：
>
> ```c
> __attribute__((section(".ccmram")))
> uint8_t fast_buffer[1024];
> ```
>
> 编译器会把 `fast_buffer` 放入目标文件的 `.ccmram` 输入段。也可以按用途为对象指定不同的输入段名称：
>
> ```c
> __attribute__((section(".ccmram.filter")))
> float filter_workspace[256];
> 
> __attribute__((section(".ccmram.control")))
> uint32_t control_workspace[128];
> ```
>
> 此时目标文件中可以出现 `.ccmram.filter`、`.ccmram.control` 等多个输入段。这里的“多个段”只是编译阶段对不同对象的分类，并不表示物理 CCMRAM 被自动划分成多个独立内存区域。本项目的链接脚本使用以下规则收集这些输入段：
>
> ```ld
> .ccmram (NOLOAD) :
> {
>     . = ALIGN(4);
>     _sccmram = .;
>     *(.ccmram)
>     *(.ccmram*)
>     . = ALIGN(4);
>     _eccmram = .;
> } > CCMRAM
> ```
>
> 括号外的 `*` 表示匹配所有参与链接的目标文件，`.ccmram*` 中的 `*` 则表示匹配段名的任意后缀。因此，`*(.ccmram*)` 可以匹配 `.ccmram`、`.ccmram.filter` 和 `.ccmram.control` 等输入段。前面的 `*(.ccmram)` 已经先收集名称完全相同的输入段，后面的规则不会再将同一输入段放置一次。
>
> 这些输入段最终会被依次合并到同一个 `.ccmram` 输出段，并整体放入链接脚本中名为 `CCMRAM` 的物理内存区域。除非链接脚本进一步定义多个输出段和明确的边界，否则程序不应把不同后缀理解为彼此隔离的内存分区，也不应依赖它们之间的排列顺序。
>
> 该输出段带有 `NOLOAD` 属性，而且本项目启动代码不会复制或清零这一区域。因此，即使对象具有静态存储期，也不能依赖其上电初值或自动清零，使用前必须由程序显式初始化。同时，CCMRAM 不能作为 DMA 缓冲区；它更适合由 CPU 高频访问的算法工作区或临时数组。
>

### 独立分段与段回收

`-ffunction-sections` 和 `-fdata-sections` 是编译选项。前者让编译器尽量把每个函数放入独立输入段，例如将函数 `HAL_RTC_MspInit()` 放入 `.text.HAL_RTC_MspInit`；后者以类似方式把各数据对象放入独立输入段。它们只负责拆分代码和数据，本身不会删除任何内容。

`--gc-sections` 是链接器选项，其中 `gc` 表示垃圾回收。链接器从程序入口和必须保留的内容出发，根据符号引用与重定位关系判断哪些输入段仍然可达，再删除不可达的输入段。通过 GCC 驱动链接器时，该选项通常写作 `-Wl,--gc-sections`，其中 `-Wl,` 表示把后面的参数传递给链接器。

这些选项配合后，链接器可以按函数或数据对象的粒度删除未使用内容。**如果多个函数仍位于同一个输入段中，只要其中一个函数被引用，整个输入段通常都必须保留**。需要注意，函数被内联、编译器启用链接时优化（LTO）或目标平台采用不同命名规则时，不一定会生成名称与函数一一对应的独立输入段。

目标文件中的段地址通常从零开始或仍为待重定位状态。这些地址不是 MCU 运行时地址；**必须完成最终链接后，才能从 ELF 或 Map 文件中得到确定地址**。

## 连接器如何分配地址

### MEMORY 与 SECTIONS：定义内存区域和输出段

GNU ld 链接脚本主要包含 `MEMORY` 和 `SECTIONS` 两部分。

**MEMORY：声明可用物理区域**

以 STM32F407 为例：

```ld
MEMORY
{
    RAM    (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
    CCMRAM (xrw) : ORIGIN = 0x10000000, LENGTH = 64K
    FLASH  (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
}
```

`ORIGIN` 是起始地址，`LENGTH` 是长度，`rx`、`rw`、`xrw` 描述区域预期具备的读、写、执行属性。这些定义必须与具体芯片型号和实际硬件一致；链接脚本不能创造芯片上不存在的内存。

**SECTIONS：合并输入段并选择区域**

下面的规则把所有 `.text` 和 `.text.*` 输入段合并为一个输出段，并放到 Flash：

```ld
.text :
{
    *(.text)
    *(.text*)
} > FLASH
```

### KEEP 机制：以 FinSH 命令表为例

`--gc-sections` 依据链接时可见的引用关系保留输入段，但有些对象并**不通过普通函数调用或变量引用被访问**，而是由程序在运行时按照一段连续地址进行枚举。FinSH/MSH 命令表就是这种情况。

例如：

```c
MSH_CMD_EXPORT(version, show RT-Thread version information);
```

该宏不仅导出命令函数，还会生成一个 `struct finsh_syscall` 命令描述对象。这个对象记录命令名称、说明和函数地址，并通过 `RT_SECTION("FSymTab")` 放入 `FSymTab` 输入段。其关系可以简化为：

```text
命令函数 version
    └─ 通常位于 .text.version

命令描述对象 __fsym_version
    └─ 位于 FSymTab
       ├─ 命令名称
       ├─ 命令说明
       └─ 指向 version 的函数指针
```

本项目的链接脚本使用以下规则收集命令描述对象：

```ld
FSymTab :
{
    . = ALIGN(4);
    __fsymtab_start = .;
    KEEP(*(FSymTab))
    __fsymtab_end = .;
    . = ALIGN(4);
} > FLASH
```

`KEEP(*(FSymTab))` 表示即使启用了 `--gc-sections`，也不得删除匹配的 `FSymTab` 输入段。链接器把所有命令描述对象连续排列在 Flash 中，并通过 `__fsymtab_start` 和 `__fsymtab_end` 标记范围。FinSH 初始化时遍历这段范围，从而发现所有导出的命令。

**命令描述对象中保存了命令函数地址**，因此保留 `FSymTab` 后，相应命令函数通常**也会因引用关系而被保留**。`RT_USED` 主要防止编译器省略命令描述对象，`KEEP()` 则防止链接器在段回收时删除它，两者作用于不同阶段。中断向量表、RT-Thread 自动初始化表等通过边界符号枚举的内容也需要采用类似的保留机制。

### 总结

链接器维护一个位置计数器 `.`。它按照脚本顺序放置输出段，每放入一项就向后推进地址，同时执行 `ALIGN()` 所要求的对齐。最终地址中可能存在对齐填充，因此不能简单地把源码对象大小相加来推算段末地址。

如果某个输出段超过所属 `MEMORY` 区域，链接器会直接失败，例如：

```text
region `RAM' overflowed by 1024 bytes
```

这类错误表示静态布局无法放入物理内存。它不同于运行时堆耗尽或栈溢出：后两者可能在链接成功后才发生。

## VMA 与 LMA

有**初值**的**全局变量**同时涉及两个地址：

```c
int system_state = 10;
```

它**运行时**必须位于 RAM 才能修改，但**初始值 `10` 必须保存在掉电不丢失的 Flash** 中。因此 `.data` 具有：

- VMA（Virtual Memory Address）：运行时访问地址，位于 RAM；
- LMA（Load Memory Address）：固件保存初值的地址，位于 Flash。

链接脚本使用下面的形式表达这种关系：

```ld
_sidata = LOADADDR(.data);

.data :
{
    _sdata = .;
    *(.data*)
    _edata = .;
} > RAM AT > FLASH
```

启动代码在复位后执行：

```text
把 [_sidata, _sidata + data_size) 从 Flash 复制到 [_sdata, _edata)
```

`.bss` 没有需要保存在 Flash 中的初值，因此通常标记为 `NOLOAD`，启动代码只需把 `[_sbss, _ebss)` 清零。`NOLOAD` 表示该段不产生固件加载载荷，不代表这段 RAM 不会在运行时使用。

## Flash 中的典型布局

本项目两个 BSP 的具体起始地址不同，但 Flash 内部的用途基本一致：

```text
Flash 起始地址
├── 中断向量表
├── .text               程序代码
├── .rodata             常量和字符串
├── .rti_fn             RT-Thread 自动初始化表
├── FSymTab             FinSH/MSH 命令表
├── ARM 异常索引
├── C 运行库初始化数组
└── .data 的初始值镜像
```

`.data` 会同时消耗少量 Flash 和 RAM：Flash 保存初值，RAM 保存运行时变量。`.bss` 只消耗 RAM。调试段通常保存在 ELF 中供 GDB 使用，但**不属于可下载到 MCU Flash 的运行映像**，因此 ELF 文件大小不能直接等同于 Flash 占用。

**ELF 中的调试信息节**

> 使用 `-g` 等调试选项编译时，编译器会在目标文件中生成 DWARF 调试信息，链接器完成地址重定位后再将其合并到最终 ELF。常见调试信息节包括：
>
> | 调试信息节 | 主要内容 | 调试时的作用 |
> |---|---|---|
> | `.debug_info` | 函数、变量、作用域和数据类型 | 识别源码对象，解释结构体成员和变量类型 |
> | `.debug_line` | 源文件行号与机器指令地址的对应关系 | 设置源码断点、源码级单步、把故障地址定位到代码行 |
> | `.debug_abbrev` | `.debug_info` 使用的描述格式 | 帮助调试器解析调试信息条目 |
> | `.debug_str` | 文件名、函数名和类型名等字符串 | 为其他调试信息提供名称 |
> | `.debug_frame` | 调用栈展开规则 | 帮助 GDB 恢复上层函数的寄存器和调用栈 |
>
> 这些信息建立了源码概念与机器运行状态之间的对应关系：
>
> ```text
> 源码函数、变量和行号
>           ↕ DWARF 调试信息与符号表
> ELF 中的指令地址、寄存器和内存位置
>           ↕ GDB 与调试服务器
> MCU 当前运行状态
> ```
>
> 因此，调试时应让 GDB 加载包含符号和调试信息的 ELF，而不是只加载 BIN 或 HEX。GDB 可以依据 `.debug_line` 把源码断点转换为实际指令地址，依据 `.debug_info` 解释变量和类型，并结合栈展开信息显示调用链；分析 HardFault 时，也可以把异常栈帧中的 PC、LR 等地址映射回函数和源码行。
>
> 调试信息节通常不带 `SHF_ALLOC` 属性，不会被映射到 MCU 的运行地址，也不会进入 ELF 的可加载段，因此一般不会转换到 BIN 或 HEX，更不会占用芯片 Flash。`.symtab` 和 `.strtab` 严格来说是符号表及其字符串表，不属于 DWARF `.debug_*` 信息，但同样是地址解析和符号化的重要依据。`.ARM.exidx` 等可能被运行库用于异常展开的内容则不同，它们属于运行映像，可能实际占用 Flash。
>
> 调试信息描述的是某一次构建产生的地址布局，调试时使用的 ELF 必须与目标板上正在运行的固件完全匹配。重新编译或改变链接脚本后，即使源码看起来没有明显变化，函数和变量地址也可能移动；继续使用旧 ELF 会导致断点、变量和调用栈解析错误。删除调试信息不会阻止程序运行，但会失去源码级调试能力；较高优化级别还可能内联函数、合并代码或消除变量，因此“包含 `-g`”也不保证每个源码变量在任意时刻都可观察。
>

## RAM 中的静态区、堆和栈

RAM 的使用可以分成静态确定和运行时变化两类。

### 链接时确定的内容

`.data`、`.bss`、显式定义的数组、静态线程栈和链接器保留区都能在链接阶段确定地址。Map 文件会列出它们的起点、大小和来源目标文件。

### 动态堆

链接器只能导出一段可用地址范围，本身不会实现 `malloc()`。RT-Thread 必须显式初始化系统堆：

```c
rt_system_heap_init(heap_begin, heap_end);
```

此后 `rt_malloc()`、动态线程控制块和动态线程栈才会使用这段范围。地址空闲但没有传给内存管理器的区域，不会自动成为堆。

### 栈

Cortex-M 的栈通常从高地址向低地址增长。启动代码设置 MSP 初值，函数调用、局部变量、寄存器保护和异常现场会在运行时改变栈深度。链接器可以安排栈顶并预留预算，但不能预知最深函数调用和最多中断嵌套。

RT-Thread 中还要区分：

- MSP：复位启动和异常/中断处理使用；
- 线程栈：每个 RT-Thread 线程独立拥有，启用动态堆时通常从系统堆申请。

如果**堆向高地址扩展、MSP 从高地址向低地址扩展**，二者之间必须保留安全距离。链接成功只能证明静态布局没有越界，不能自动证明运行时不会发生堆栈碰撞。

## STM32F407 在本项目中的布局

具体定义见 [`BSP/STM32F4/STM32F407xx_FLASH.ld`](../BSP/STM32F4/STM32F407xx_FLASH.ld)。

### 物理区域

```text
FLASH   0x08000000 ～ 0x080FFFFF    1024 KiB
CCMRAM  0x10000000 ～ 0x1000FFFF      64 KiB
RAM     0x20000000 ～ 0x2001FFFF     128 KiB
```

CCMRAM 与主 SRAM 不连续。当前 `.ccmram` 被定义为 `NOLOAD`，启动代码不会复制或清零它，其中对象必须由使用者主动初始化。CCMRAM 仅供 CPU 使用，不能放置 DMA 缓冲区。

### 主 SRAM

当前策略让 RT-Thread 系统堆自动占用静态数据后的剩余主 SRAM，同时在顶部保留 8 KiB MSP 空间：

```text
0x20000000 ┌─────────────────────────┐
           │ .data                   │
           │ .bss                    │
heap_start ├─────────────────────────┤  ALIGN(_ebss, 8)
           │ RT-Thread system heap   │
heap_end   ├─────────────────────────┤  0x2001E000
           │ MSP reserve: 8 KiB      │
0x20020000 └─────────────────────────┘  _estack
```

链接脚本导出 `__heap_start__` 和 `__heap_end__`，[`BSP/STM32F4/Ports/board.c`](../BSP/STM32F4/Ports/board.c) 将其传给 `rt_system_heap_init()`。因此新增全局变量使 `.bss` 增大时，堆起点和堆容量会自动调整。

`__msp_stack_limit__` 是软件约定边界，不是 Cortex-M4 的硬件越界保护。MSP 若实际使用超过 8 KiB，仍可能进入系统堆，需要通过栈填充水位、异常压力测试或 MPU 保护验证。

## CC2538 在本项目中的布局

具体定义见 [`BSP/CC2538/cc2538_512_gcc.ld`](../BSP/CC2538/cc2538_512_gcc.ld)。

### Flash 与 CCA

```text
应用 Flash  0x00200000 ～ 0x0027FFD3
CCA         0x0027FFD4 ～ 0x0027FFDF    12 bytes
```

CC2538 的程序 Flash 从 `0x00200000` 开始。末尾的 Customer Configuration Area 是芯片启动流程要求的硬件配置区域，必须保持固定地址，不能把它当作普通代码空间使用。

### 两块 16 KiB SRAM

CC2538 的 32 KiB SRAM 地址连续，但低功耗保持能力不同：

```text
0x20000000 ┌─────────────────────────┐
           │ 16 KiB non-retention    │ RT-Thread system heap
0x20004000 ├─────────────────────────┤
           │ 16 KiB retention        │ .data + .bss + startup stack
0x20008000 └─────────────────────────┘
```

当前工程把整个 non-retention SRAM 作为 RT-Thread 堆：

```text
__rt_heap_start = 0x20000000
__rt_heap_end   = 0x20004000
```

有初值变量、零初始化变量和启动栈位于 retention SRAM。初始化逻辑见 [`BSP/CC2538/Ports/board.c`](../BSP/CC2538/Ports/board.c)，启动复制和清零逻辑见 [`BSP/CC2538/startup_gcc.c`](../BSP/CC2538/startup_gcc.c)。

该布局可以完整利用低地址 16 KiB，但不能在进入 PM2/PM3 后原地恢复 RT-Thread：动态线程栈、线程控制块及其他堆对象可能位于 non-retention SRAM，唤醒后内容不再可靠。如果需要深度低功耗恢复，应把必须保持的堆和线程对象放入 retention SRAM，并把低地址区域作为唤醒后可重新初始化的临时内存池。

## 如何查看最终地址

本项目应先在 PowerShell 中查看并选择当前实际可用的 BSP 与构建类型 Preset。例如构建 Debug 固件：

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
cmake --list-presets=configure
cmake --list-presets=build

cmake --preset stm32f4-debug
cmake --build --preset stm32f4-debug

cmake --preset cc2538-debug
cmake --build --preset cc2538-debug
```

需要发布构建时，使用对应的 `stm32f4-release` 或 `cc2538-release`。Debug 与 Release 使用不同构建目录，分析地址或调试时必须使用与目标固件来自同一构建目录的 ELF 和 Map。

构建完成后，可以从以下文件判断实际分配结果：

| 文件或工具 | 适合查看的内容 |
|---|---|
| `.map` | 输出段地址、符号地址、每个目标文件的贡献、丢弃段 |
| `.elf` | 完整段表、符号表、调试信息和加载信息 |
| `.hex` | 带目标地址的可下载数据记录 |
| `.bin` | 连续原始数据，不自行携带目标地址语义 |
| `arm-none-eabi-size` | Flash/RAM 分类后的总体尺寸 |
| `arm-none-eabi-objdump -h` | ELF 中每个段的地址、大小和属性 |
| `arm-none-eabi-nm -n` | 按地址排序查看最终符号 |

判断 RAM 占用时不能只看 `bss` 数字，因为系统堆和运行时栈可能由链接符号描述而不计入普通 `.bss`。判断 Flash 占用时，也应考虑 `.data` 初值镜像和段间对齐，而不能只看 `.text`。
